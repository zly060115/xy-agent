## 一、项目定位

XY 是一个**跑在用户自己电脑上的文档分析型 Agent**：给它文件或一句话目标，它自己规划步骤、调用工具、读文档、查知识库、写文件，直到把事情办完。数据不出本机。

### 它解决什么问题

| 痛点 | 常见做法 | XY 的做法 |
|---|---|---|
| 长文档读不完 | 把整篇塞给模型 | 按章节切段、逐段抽事实、代码拼装，7 段结构化报告 |
| 模型编数字 | 相信模型输出 | 数值溯源 + 章节覆盖 + 结构完整三项确定性核对，疑点如实写进报告 |
| 云端模型传文档有顾虑 | 上传到第三方 | 默认本地 Ollama；换云端时密钥只存本机 `settings.json` |
| Agent 乱读乱写文件 | 全盘权限 | 读走白名单 + 人工确认；写走四道校验 + 扩展名白名单 |
| 小模型工具调用不稳 | 靠提示词硬压 | 消息格式统一转换、两阶段自检、谎报拦截、格式兜底重试 |

### 设计取向

- **零 Agent 框架**：不用 LangChain / LlamaIndex / AutoGen。ReAct 循环、工具调度、上下文拼装全部手写，约 6000 行，每一行都能讲清楚为什么在。
- **代码兜底优先于提示词**：模型不可靠的地方（数字、章节完整性、标记泄漏、假成功）全部用确定性代码补，而不是反复调提示词。
- **失败要看得见**：检索失败写日志、报告写「覆盖范围」、自检写疑点，不做静默降级。

### 项目规模

| 部分 | 文件数 | 行数 |
|---|---|---|
| 核心引擎 `myagent/` | 17 个 .py | 约 6072 |
| 网页端 `web.py` | 1 | 785 |
| 桌面外壳 `desktop.py` | 1 | 约 300 |
| 命令行 `main.py` | 1 | 约 230 |

```bash
# 1. 虚拟环境
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

# 2. 本地模型（不跑本地可跳过，改用云端 API）
ollama pull qwen2.5:7b          # 对话 + 工具调用

.venv\Scripts\python.exe web.py         # 网页端 http://127.0.0.1:7860
.venv\Scripts\python.exe main.py        # 命令行

└───────────────────────────┬──────────────────────────────────┘
                            │ 都是同一套 Agent 实例（runtime 单例）
┌───────────────────────────▼──────────────────────────────────┐
│ 编排层  agent.py                                              │
│  自动 RAG 注入 → LLM 决策 → 工具调度 → 结果回填 → 循环         │
│  特殊处理：计划识别、数字复核、谎报拦截、标记剥离               │
└──────┬───────────────────────────────────────┬───────────────┘
       │                                       │
┌──────▼──────────────┐              ┌─────────▼───────────────┐
│ 能力层               │              │ 基础设施层               │
│ tools.py  13 工具    │              │ llm.py   双后端          │
│ analyst.py 文档分析   │              │ rag.py   Chroma 双集合   │
│ checks.py 自检        │              │ safe_reader.py 只读解析  │
│ image_reader.py 图像  │              │ confirm.py 确认网关      │
│ skills.py 技能注入    │              │ memory.py 长期记忆       │
└──────────────────────┘              │ settings.py 配置持久化   │
                                      └─────────────────────────┘
```

### 一次对话的完整数据流

```
用户输入
  │
  ├─▶ memory.py        取出本会话历史（最近 N 轮）
  │
  ├─▶ rag.py.search()  自动检索知识库 top_k=5
  │                    → 命中则拼成「参考资料」注入 system 片段
  │                    → 每条带「来源：<文件名>」
  │
  ├─▶ agent.py 组装 messages
  │     system: BASE_PROMPT + 技能片段 + 知识库片段 + 当前时间/可写目录
  │     user:   本轮问题
  │
  ├─▶ llm.chat(messages, tools=13 个 schema)
  │     │
  │     ├─ 返回 tool_calls ──▶ execute_tool()
  │     │                       ├─ 敏感工具 → confirm.py 等用户点头
  │     │                       ├─ 执行 → 结果作为 tool 消息回填
  │     │                       └─ 回到 llm.chat（最多 15 步）
  │     │
  │     └─ 返回纯文本 ──▶ 收尾
  │
  ├─▶ 收尾处理
  │     scrubbed_rag_tags()   剥掉模型抄出来的 [知识库·x] 标记
  │     _claims_write()       拦截「说写完了其实没写」
  │     memory.py 写入长期记忆（失败的伪成功不写）
  │
  └─▶ 返回用户
```

### 为什么不用框架

| 框架方案 | 问题 |
|---|---|
| LangChain AgentExecutor | 循环黑盒，7B 模型出错时拿不到中间态，改一个行为要翻框架源码 |
| LlamaIndex RAG | 切分/检索策略固定，中文短问句召回差，重排插不进去 |
| 自研 | 全部可控：错误可见、每步可测、6000 行够读 |

## 五、核心模块

### 5.1 执行引擎 `agent.py`

ReAct 循环 + 原生 Function Calling，`max_steps` 默认 15。

```python
class Agent:
    def run(self, user_input: str) -> str:
        # 1. 组装上下文（技能 / 知识库 / 历史）
        # 2. for step in 1..max_steps:
        #       reply = llm.chat(messages, tools=specs)
        #       if not reply.tool_calls: break
        #       for call in reply.tool_calls:
        #           result = execute_tool(name, args)
        #           messages.append(tool_result)
        # 3. 收尾：剥标记、核数字、写记忆
```

**几个非标准但必要的补丁**（都是踩坑后加的）：

| 机制 | 触发条件 | 行为 |
|---|---|---|
| 计划识别 `_looks_like_plan` | 模型只说「我将要…」却没调工具，且未到步数上限 | 打回一次，要求直接执行 |
| 数字复核 `_number_retry` | 回答里的数字在工具结果里找不到 | 重问一次，最多 1 次 |
| 谎报拦截 `_claims_write` | 回复声称「已创建/已写入」但本轮没有 `write_file` 成功记录 | 打回；仍不做则标注未完成，且不写入长期记忆 |
| 标记剥离 `scrubbed_rag_tags` | 回复含 `[知识库·xxx]` | 代码层确定性删除，不靠提示词 |
| 异常汉化 | `llm.chat` 抛异常 | 统一走 `_explain()` 转成中文建议，不甩英文堆栈 |

### 5.2 模型接入 `llm.py`

两套后端，统一接口 `BaseLLM.chat(messages, tools, options)`：

| 后端 | 类 | 通道 | 用于 |
|---|---|---|---|
| 本地 | `OllamaLLM` | Ollama 原生 API | `ollama pull` 的模型 |
| 云端 | `OpenAICompatLLM` | OpenAI 兼容 `/v1/chat/completions` | 13 家厂商 + 自定义 |

**厂商差异只在 `base_url` + 模型名**，所以 12 家云端厂商共用一个类。见 `providers.py`：

| id | 厂商 | 默认 base_url | 首个推荐模型 |
|---|---|---|---|
| `ollama` | 本地 Ollama（免密钥） | `http://localhost:11434` | qwen2.5:7b |
| `deepseek` | DeepSeek 深度求索 | `https://api.deepseek.com` | deepseek-flash |
| `dashscope` | 阿里云百炼（通义千问） | `https://dashscope.aliyuncs.com/compatible-mode/v1` | qwen3.8-max |
| `zhipu` | 智谱 GLM | `https://open.bigmodel.cn/api/paas/v4` | glm-5.3 |
| `moonshot` | 月之暗面 Kimi | `https://api.moonshot.cn/v1` | kimi-k3.1-pro |
| `ark` | 字节豆包（火山方舟） | `https://ark.cn-beijing.volces.com/api/v3` | doubao-seed-2-1-pro |
| `hunyuan` | 腾讯混元（TokenHub） | `https://tokenhub.tencentcloudmaas.com/v1` | hy3 |
| `minimax` | MiniMax | `https://api.minimaxi.com/v1` | MiniMax-M3 |
| `stepfun` | 阶跃星辰 | `https://api.stepfun.com/v1` | step-3.7-flash |
| `siliconflow` | 硅基流动 | `https://api.siliconflow.cn/v1` | DeepSeek-V4-Flash |
| `openai` | OpenAI | `https://api.openai.com/v1` | gpt-4o-mini |
| `openrouter` | OpenRouter | `https://openrouter.ai/api/v1` | openai/gpt-4o-mini |
| `custom` | 自定义兼容接口 | 用户填 | 用户填 |

**三个关键实现细节**：

1. **消息格式转换** `_to_openai_msg()`
   Ollama 返回的 `tool_calls` 是扁平结构 `{id, name, arguments}`，OpenAI 要求 `{id, type:"function", function:{name, arguments}}`。直接透传会导致第二轮请求 422（`messages[4]` 缺字段）。发送前统一转换，`tool` 消息只留 `tool_call_id`，`content=None` 补空串。

2. **地址规范化** `normalize_base_url()`
   用户填 `https://api.deepseek.com` 时自动补 `/v1`；已经带路径的不动（避免 `/v1/v1`）。

3. **两阶段自检** `ping(llm, check_tools=True)`
   先发一条普通对话确认连通，再真实跑一次 `calculator` 工具往返。
   只测连通会出现「测试通过但实际用不了」——工具调用格式错了只有跑到第二轮才炸。

### 5.3 工具系统 `tools.py`

13 个工具，JSON Schema 原生定义，无装饰器魔法。

| 工具 | 作用 | 需确认 | 参数 |
|---|---|---|---|
| `now` | 当前日期时间星期 | — | — |
| `list_files` | 列工作区目录 | — | `path` |
| `read_file` | 读工作区文本 | — | `path` |
| `write_file` | 写文件（txt/md/docx/csv/json） | — | `path`, `content` |
| `run_command` | 工作区内执行 shell | ✅ | `command` |
| `search_web` | DuckDuckGo 联网检索 | — | `query` |
| `calculator` | 精确四则运算 | — | `expression` |
| `search_knowledge` | 查本地知识库 | — | `query`, `top_k` |
| `knowledge_stats` | 知识库容量与路径 | — | — |
| `list_local_files` | 列授权目录可解析文件 | ✅ | `directory` |
| `read_local_file` | 读授权目录文件 | ✅ | `path` |
| `analyze_document` | 通读文档/图片出结构化结论 | ✅ | `path` |
| `ingest_local_file` | 解析入库 | ✅ | `path` |

**工具选择提示词策略**：`write_file` 的 description 里动态拼接了真实可写目录（`_write_roots()`），这样 7B 模型不用猜路径，也避免"请提供路径"这种反问。

**执行入口**：

```python
from myagent.tools import execute_tool
result = execute_tool("calculator", {"expression": "(29*12)+99"})
# → "计算结果：447"
```

敏感工具在执行前会经过 `confirm.py`，用户拒绝则返回拒绝信息给模型，模型会改方案而不是死循环。

### 5.4 RAG 知识库 `rag.py`

**双集合设计**（同一个 Chroma 实例，两个 collection）：

| 集合 | 内容 | 用途 |
|---|---|---|
| `knowledge_files` | 入库文档切片 | 回答文档相关问题 |
| `chat_memory` | 长期记忆条目 | 跨会话记住用户偏好/事实 |

分开的原因：清空知识库不能把记忆一起清掉，反之亦然。

**切分策略**（`split_text`）：

- 按章节累积：小段落合并到接近 600 字，遇到新章节才断开
- 只在顶层标题切（一、二、三 / 第X章 / markdown `#`），`1.` `(1)` 这类次级编号留在正文
- 超长段落硬切，`overlap=0`（中文重叠反而降低召回）

**混合检索重排**（`search`）：

```
最终分 = 0.7 × 向量余弦相似度 + 0.3 × 二字覆盖率
```

只用向量时，中文短问句的相似度全挤在 0.65~0.75，区分不开；补一个「查询二字组在片段里出现了多少」的覆盖度，能明显拉开排序。

**健壮性处理**：

- 跳过 `documents=None` 的脏记录（旧版本写入异常留下的）
- 索引越界保护
- 空文本 `_coverage()` 返回 0 而不是抛异常
- 检索失败写日志留痕，不再被 `except: pass` 吞掉

**典型用法**：

```python
from myagent.rag import RAGStore, build_embed_fn
from myagent.config import config

store = RAGStore(config.chroma_dir, embed_fn=build_embed_fn())
store.add_file_chunks(path, chunks, source="合同.pdf")
hits = store.search("违约金怎么算", top_k=4)
stats = store.stats()   # {'knowledge_chunks': 31, 'memory_chunks': 28, 'db_path': ...}
```

### 5.5 文档分析 `analyst.py`

7B 模型的注意力覆盖不住长文，整篇送进去通常只抓开头就收尾。所以拆成"逐段抽事实 → 代码拼装"。

**参数**：

| 常量 | 值 | 含义 |
|---|---|---|
| `TINY_LIMIT` | 600 字 | 短于此跳过逐段抽取，直接一次分析 |
| `SEG_SIZE` | 1200 字 | 每段上限 |
| `MAX_TOTAL` | 200,000 字 | 总字数上限，超出明确告知截断 |
| `MAX_SEGMENTS` | 30 | 段数上限 |
| 并发 | 3 路 | 14 段从 6 分钟压到 75 秒 |

**固定 7 段输出**：

```
文档概况 → 文档结构 → 逐部分要点 → 关键数据
→ 涉及人员 → 结论与要求 → 疑点与风险 → 覆盖范围
```

其中「逐部分要点」由代码拼装（模型组装时会整节漏掉，实测漏过一整节）；「关键数据」模型漏了就从原文扫数字兜底。

**流式进度**：`analyze_fn` 是生成器，通过 Gradio 的 yield 逐条推送「正在抽取第 3/14 段…」，长文档不白屏。

### 5.6 报告自检 `checks.py`

分析结束后用确定性代码核对三项，**有疑点写进报告的「自检」一节，而不是偷偷改掉**——悄悄修正会让整份报告看起来都可信，更危险。

| 检查 | 判据 | 减少误报的处理 |
|---|---|---|
| 数值溯源 | 「关键数据」里每个数要能在原文找到 | 千分位、全角、`1.5万→15000`、两数加减的汇总值都算命中 |
| 章节覆盖 | 原文标题被提及比例 < 60% 才提示 | 摘要式报告本来就不点章节名 |
| 结构完整 | 概况/关键数据/结论三节是否齐全 | 只卡决策必需的三项 |

另有 `number_guard()`：对话回答里出现的数字若在工具结果中找不到，追加一条提示。

### 5.7 安全机制

**读：三层防护**（`safe_reader.py`）

1. 白名单目录：`ALLOWED_FILE_DIRS` + `DATA_DIR`/uploads/workspace 自动加入
2. `FORBIDDEN_DIRS`：Windows、Program Files、AppData 等，即使配进白名单也强制排除
3. 路径校验：解析真实路径（`realpath`）后判断是否在根内、禁止符号链接、扩展名白名单、单文件 50MB 上限

**写：四道校验**（`tools._write_blocker()`）

1. `FORBIDDEN_DIRS` 命中直接拒
2. 必须落在允许的写根（工作区 + `ALLOWED_WRITE_DIRS`，默认桌面/文档/下载）
3. 扩展名白名单：`.txt .md .docx .csv .json`
4. 任何异常一律拒绝（fail-closed）

`write_file` 拿不到合法路径时返回明确原因（`_where_label()`），不会静默写进工作区。

**确认网关**（`confirm.py`）

| 模式 | 场景 | 行为 |
|---|---|---|
| `terminal` | 命令行 | 终端 y/n，超时 120s |
| `callback` | 网页/桌面 | 回调给 UI；没有回调时立即拒绝，不空等 |
| `auto_deny` | 无人值守 | 一律拒绝 |

### 5.8 记忆系统 `memory.py`

| 层 | 存储 | 生命周期 |
|---|---|---|
| 会话历史 | 内存 list | 单次会话，可重置 |
| 长期记忆 | Chroma `chat_memory` | 跨会话，按相似度召回 |

写入规则：**假成功不写**。模型声称写了文件但实际没写的那一轮，既不标注完成也不写入记忆，避免"污染后反复复述"。

`FAILURE_MARKS` 里维护了一批失败话术（「请提供文档的路径」「无法直接在桌面创建」「权限限制」等），命中则不算有效经验。

### 5.9 技能系统 `skills.py`

兼容 `SKILL.md` 约定，放在 `{DATA_DIR}/skills/<名字>/SKILL.md`：

```markdown
---
name: doc-analysis
description: 分析合同、报告、纪要时的输出规范与自检清单
keywords: 文档,分析,合同,报告,风险
---
# 正文
```

**只注入命中的那一份**。8192 上下文里塞多份技能，7B 会把 A 的步骤套到 B 上，还会挤掉工具定义。匹配走「关键词直接命中 + 二元字重叠」两条路取高者。内置一份 `doc-analysis`。

### 5.10 图像理解 `image_reader.py`

文档里内嵌的图，两级处理：

1. **OCR 优先**（RapidOCR）：准、快、不占显存，能抽出字的图到这一步就结束
2. **视觉模型兜底**：OCR 抽不出字（纯图表/照片）才送多模态模型

受 `MAX_IMAGES`（12 张）和 `MAX_VISION_IMAGES`（6 张）限制，防止几十张图跑很久。识别不到的内容会在报告「覆盖范围」里如实写出。

### 7.2 HTTP API

服务启动后，接口文档地址：`http://127.0.0.1:7860/gradio_api/info`

**实测注册的 10 个端点**：

| 端点 | 输入（data 数组） | 输出 |
|---|---|---|
| `/chat` | `[message: str, history: list]` | `["", history]` — 输入框清空 + 新历史 |
| `/reset` | `[]` | `[[] , ""]` |
| `/analyze` | `[file: FileData, also_ingest: bool]` | 文本（**流式**：多帧 generating） |
| `/ingest` | `[file: FileData]` | 入库结果文本 |
| `/stats` | `[]` | 知识库状态文本 |
| `/provider_info` | `[provider_id: str]` | 6 项组件更新：模型列表/地址/说明/视觉模型/选中卡片/密钥 |
| `/test_model` | `[pid, model, key, base_url, vision]` | `✅/❌ + 说明` |
| `/apply_model` | 同上 | 保存并热切换的结果 |
| `/clear_model` | `[]` | 清除结果 |
| `/save_style` | `[style: str]` | 保存结果 |

> 内部回调（`chat_fn`、`pick_model_fn`、`model_status_fn` 等）均设为 `api_visibility="private"`，不会注册成 HTTP 路由。

#### 调用协议（Gradio 6）

两步：先提交拿 `event_id`，再读 SSE 流。

```bash
# 1. 提交
curl -X POST http://127.0.0.1:7860/gradio_api/call/stats \
     -H "Content-Type: application/json" -d '{"data":[]}'
# → {"event_id":"aa68e71809ab4f6291448dba3e48e348"}

# 2. 读结果
curl http://127.0.0.1:7860/gradio_api/call/stats/aa68e71809ab4f6291448dba3e48e348
```

返回是 `text/event-stream`：

```
event: heartbeat
data: null

event: complete
data: ["知识库片段: 31\n记忆片段  : 29\n数据库路径: C:\\Users\\zly\\.xy\\chroma_db\n..."]
```

事件类型：`heartbeat`（保活）、`generating`（流式中间帧，`/analyze` 会连续出现）、`complete`（最终结果）、`error`（异常）。

#### `/chat` 的实测请求与响应

```bash
curl -X POST http://127.0.0.1:7860/gradio_api/call/chat \
  -H "Content-Type: application/json" \
  -d '{"data":["你叫什么名字？",[]]}'
```

```json
["", [
  {"role":"user","metadata":null,"options":null,
   "content":[{"text":"你叫什么名字？","type":"text"}]},
  {"role":"assistant","metadata":null,"options":null,
   "content":[{"text":"我叫XY。","type":"text"}]}
]]
```

注意：Gradio 6 的 Chatbot 用 **messages 格式**，`content` 是 block 数组（`{text, type}`），不是纯字符串。客户端解析时取 `content[0].text`。

#### 推荐用 Python 客户端

手写 SSE 容易踩坑，`gradio_client` 随 Gradio 一起装好，一行搞定：

```python
from gradio_client import Client, handle_file

c = Client("http://127.0.0.1:7860/", verbose=False)

# 对话
c.predict("你好", [], api_name="/chat")

# 文档分析（handle_file 会自动上传本地文件）
report = c.predict(handle_file(r"C:\Users\zly\Desktop\合同.pdf"), False, api_name="/analyze")
print(report)

# 入库
c.predict(handle_file(r"C:\Users\zly\Desktop\手册.docx"), api_name="/ingest")

# 状态
print(c.predict(api_name="/stats"))
```

## 九、桌面版实现

`desktop.py` 是 pywebview 外壳，不改 `web.py` 一行代码。

### 启动流程

```
双击 desktop.bat（pythonw，无控制台）
  │
  ├─ 1. 开窗口，立刻渲染本地 splash（logo + 状态文字 + 进度条）
  │      用户不会再对着桌面发呆
  │
  ├─ 2. 后台线程：import web → demo.launch(prevent_thread_lock=True)
  │      Gradio 装配路由（chromadb、onnxruntime 都在这一步加载）
  │
  ├─ 3. 轮询首页等到 HTTP 200（不是端口 listen —— 中间有几秒 404）
  │
  └─ 4. window.load_url() 切到真实界面
```

实测：冷启动约 6 秒，复用已有实例约 1 秒。

### 三个关键设计

| 问题 | 处理 |
|---|---|
| 端口被占 | 先请求 `/config` 看 title 是不是自己：是就直接接入复用，不是才换端口（+1 起找 20 个） |
| 关窗不退出 | `demo.close()` + `os._exit(0)` 兜底。Gradio 服务线程不是 daemon，不清会在任务管理器留 `python.exe`，下次启动撞端口 |
| pythonw 无 stdout | 启动时把 `sys.stdout/stderr` 重定向到 `~/.xy/desktop.log`。否则任何 `print` 都抛 `AttributeError` 静默死掉 |

### 调试

```bash
desktop.bat -d     # 保留控制台 + 窗口内可开 F12 开发者工具
```

日志：`~/.xy/desktop.log`（含状态推进与异常堆栈）。

## 十一、已知限制

| 限制 | 现状 | 影响 |
|---|---|---|
| 单 Agent 实例 | `runtime.py` 全局单例，会话共享一份历史 | 多人同时用会串话；本地单人场景无影响 |

| 检索质量 | 混合重排（0.7 向量 + 0.3 覆盖） | 极短查询（1~2 字）召回仍偏弱 |
| 7B 能力边界 | 复杂多步推理会偷懒 | 靠步数上限 + 计划打回兜底 |
| 思考型模型 | `deepseek-r1` 等思考会吃 token | 空正文时提示「预算被思考占满」 |
| Windows only | 路径、`.doc`、桌面壳均按 Windows 实现 | macOS/Linux 需改 `desktop.py` 与 `.doc` 分支 |

## 十二、故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 双击没反应 | 端口被占 / venv 缺失 / pythonw 崩溃 | 看 `~/.xy/desktop.log`；`desktop.bat -d` 看控制台 |
| 页面一直转圈 | Ollama 没起 / 模型没 pull | `ollama list` 确认；`curl http://localhost:11434/api/tags` |
| 云端模型第二轮报 422 | 工具消息格式不兼容 | 已由 `_to_openai_msg()` 统一转换；升级到最新版 |
| 测试连接通过但用不了 | 只测了连通没测工具往返 | 用「测试连接」的两阶段自检（会真跑一次 calculator） |
| 知识库明明入库了却检索不到 | 检索失败被吞 / 脏记录 | 看 `web.log`；`knowledge_stats` 核对片段数 |
| 模型说「请提供文档路径」 | 提示词把知识库问题引向文件读取 | 已在 BASE_PROMPT 加硬规则；确认用的是最新提示词 |
| 模型自称旧名字 | 长期记忆里存着改名前的对话 | 跑 `.workbuddy/memory_rebrand.py --apply` 迁移记忆 |
| 改了名但界面还是旧的 | 连的是旧实例（`/config` title 不匹配） | 关掉旧进程再启，或访问新端口 |
| 桌面上写不了文件 | 目标不在允许写目录 / 扩展名不在白名单 | 支持 `.txt .md .docx .csv .json`；目录看界面「知识库」页的可写列表 |
| 上传大文件很慢 | 解析 + OCR + 逐段分析 | 正常；2 千字约 1 分钟，1.4 万字约 75 秒（RTX 4060） |
