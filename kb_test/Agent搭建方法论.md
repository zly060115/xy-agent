# Agent 搭建方法论（《48 页教程》+ 实战清单）

来源：一张《3.5 小时练完这 48 页，你的 Agent 搭建就牛了》保姆级教程流程图，以及作者 Jennie（俄语入局 AI）的 18 条补充说明。以下是整理后的要点。

## 一句话主线

**先把最小可用的搭起来，再按遇到的问题逐个加能力。** 不要一上来就微调模型、不要一上来就上多智能体——90% 的场景，Prompt + RAG + 工具三样就够了。

## 基础 6 件套（所有智能体必装）

**六件套 = LLM（大脑）+ Prompt（岗位说明书）+ Context（记忆窗口）+ Token（额度上限）+ Temperature（发挥程度）+ Tool（工具）。** 这六样是所有智能体都要有的，缺哪一件，就会在对应的场景上翻车。

一次性列全：

- LLM：大脑，选模型
- Prompt：岗位说明书，定身份/规则/输出格式/红线
- Context：记忆窗口，记几轮历史
- Token：额度上限，管成本
- Temperature：发挥程度，严谨 0.1~0.3，发散 0.7~0.9
- Tool：工具，只加任务必需的那几个

### 1. LLM —— 大脑

选一个大模型当 Agent 的大脑。新手用通用的就行（通义千问、DeepSeek、GPT-4o），接入 API 即可，不用自己训。本地跑则用 Ollama（如 qwen2.5:7b）。

### 2. Prompt —— 岗位说明书

写清 System 提示词，等于给 Agent 一份岗位说明书：**定死身份、规则、输出格式、以及"不能做什么"**。其中"不能做什么"（红线）最容易被忽略，但对稳定性影响最大。

### 3. Context —— 记忆窗口

设置对话记忆窗口，控制能记住多少轮历史对话。设太大浪费 Token 且拖慢响应，设太小会忘掉前文。典型做法：保留最近 N 轮，更早的压缩成摘要。

### 4. Token —— 额度上限

设置单次调用和单日调用的 Token 上限，管控运行成本。本地模型没有成本，但接 API 后这是必需项，否则一个死循环就能烧掉预算。

### 5. Temperature —— 发挥程度

- **0.1 ~ 0.3**：客服、审核、数据抽取、文档分析等要严谨的场景，防瞎编
- **0.7 ~ 0.9**：文案策划、创意生成，要发散有创意

### 6. Tool —— 工具

只加任务**必须**用到的工具，比如查表格、发企微、联网搜索。多余的工具一律不加——工具越多，模型选错工具的概率越高，出错就越多。

## 按需叠加（遇到问题再加，别提前上）

### 7. RAG + 向量库（有资料需求时加）

需要读公司业务文档、规章制度时，把文件上传进向量库，让 Agent 检索内部资料。它解决两个问题：**幻觉**（模型不知道就编）和**知识过时**（训练数据是截止日期前的）。

### 8. Few-shot（输出格式不规范时加）

拿 3~5 个标准案例喂给 Agent，用最低成本对齐工作格式。**优先级远高于 Fine-tune**：改提示词只要几分钟，微调要几百上千条标注数据 + 训练时间，而且模型一换就得重来。

### 9. Tool + MCP + Skill（需要联动系统时加）

- **Tool（工具）**：单个能力，查表格、发消息、搜网页
- **MCP（统一接口协议）**：让 Agent 一键打通 CRM、OA、表格等多个外部系统，不用逐个写对接代码。相当于"外部系统的通用插座"
- **Skill（技能包）**：把反复使用的流程打包成技能，后续可以给其他 Agent 直接复用。相当于"写好的操作手册"

### 10. Harness / 多智能体（多角色协作时加）

多个分工不同的 Agent 协同工作时，用 Harness 来调度流程、处理任务报错和重试。单 Agent 能搞定的事不要上它——调度层本身就是新的故障来源。

### 11. Fine-tune 微调（最后手段）

只有 Few-shot 和 RAG 都达不到专业要求时，才用批量业务数据微调模型底座。成本高、迭代慢，是最后一张牌。

## Agent 执行闭环（流程图解读）

架构分层（从左到右）：**用户 → Agent 运行时 → LLM 大模型 → Agent Skills 技能 → MCP 工具协议 → 工具 / 外部系统**。

注意：这六层是**一条消息的流转路径**（运行时链路），不是前面说的"基础 6 件套"。基础 6 件套是配置项：LLM、Prompt、Context、Token、Temperature、Tool。两者不要混。

一次请求的完整链路：

1. 用户提出需求，Agent 运行时接收请求
2. 理解需求（意图识别），加载上下文
3. 记忆检索：把相关历史调进来
4. 推理：判断该用哪个模型、哪个技能（技能匹配）
5. 若需要资料，检索工具和文档，把工具配置进上下文
6. 进入 Action：推理下一步该调哪个工具
7. 执行推理与验证：工具调用、参数校验
8. 拿到结果后**返回观察**，判断任务是否完成
9. 没完成 → 带着观察结果回到第 6 步，再规划下一步（这就是 ReAct 循环）
10. 完成 → 整合最终结果，返回给用户

核心逻辑一句话：**Agent 通过理解用户需求，结合上下文和记忆进行规划推理，基于合适的 Skill 调用相应工具，并把工具结果反馈回上下文，形成"规划 → 执行 → 观察 → 再规划"的闭环。**

## 名词速查

| 名词 | 说明 |
|---|---|
| LLM | 大语言模型，Agent 的大脑 |
| Prompt | 提示词，Agent 的岗位说明书 |
| Context | 上下文/记忆窗口，能看多少前文 |
| Token | 计费与长度单位，约等于"字"的粒度 |
| Temperature | 随机性参数，低=严谨，高=发散 |
| Tool | 工具，单点能力 |
| RAG | 检索增强生成，先去资料库找，再回答 |
| Vector Database | 向量数据库，按语义相似度检索 |
| Few-shot | 给几个标准例子教格式 |
| MCP | 外部系统的统一接口协议 |
| Skill | 可复用的技能包（流程打包） |
| Harness | 多智能体调度编排层 |
| Fine-tune | 微调模型底座，成本最高的手段 |

## 判断顺序（照这个走不会错）

1. 先搭 6 件套，跑通最小闭环
2. 回答不准 / 需要内部资料 → 加 RAG
3. 格式不齐 → 加 Few-shot
4. 要操作外部系统 → 加 Tool，系统多了再上 MCP
5. 一套流程反复用 → 打包成 Skill
6. 单 Agent 忙不过来、需要多角色 → 才考虑 Harness
7. 以上都满足不了专业要求 → 最后才 Fine-tune
